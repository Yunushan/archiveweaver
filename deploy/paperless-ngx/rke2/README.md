# Paperless-ngx v3.2.1 on RKE2: release-specific reference

This is a review template for [Paperless-ngx v3.2.1](https://github.com/paperless-ngx/paperless-ngx/releases/tag/v3.2.1). It is **not a production release**. The repository has no live RKE2 target, approved OCI digest, storage class, database or broker endpoint, ingress class, certificate, production inventory, or deployment evidence. The bundle cannot render as checked in because `paperless.env` and `postgres-ca.pem` are absent. The image reference and other required site values are deliberately invalid placeholders.

The `archiveweaver` namespace and `paperless-ngx` Deployment name match the current Ansible provider contract. The bundle contains only resource kinds allowed by its first-use gate: Namespace, ServiceAccount, PersistentVolumeClaim, Deployment, Service, generated Secret, and NetworkPolicy. `ingress.yaml.example` is excluded from `kustomization.yaml` until a site-specific TLS route is reviewed. The checked-in generic `deploy/kubernetes/overlays/rke2` remains an unrelated review envelope.

## Required stack and inputs

- The [tagged upstream PostgreSQL example](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docker/compose/docker-compose.postgres.yml) uses one Paperless container on port 8000, PostgreSQL, and a Redis-compatible broker. This reference uses **external, operator-managed PostgreSQL and Valkey/Redis endpoints**. Their availability, authentication, TLS, backups, failover, network reachability, and image provenance require separate evidence. It does not deploy either dependency.
- Replace the Paperless image with the approved `ghcr.io/paperless-ngx/paperless-ngx@sha256:<digest>` for the target architecture. Verify that the digest identifies the reviewed v3.2.1 release and include image-specific signed provenance and SBOM evidence required by the release gate. Do not use `latest` or a mutable version tag as the applied image.
- Set `PAPERLESS_DBHOST`, `PAPERLESS_DBPORT`, `PAPERLESS_DBNAME`, and `PAPERLESS_DBUSER` for the selected PostgreSQL service. v3 requires `PAPERLESS_DBENGINE=postgresql`. The bundle sets `PAPERLESS_DB_OPTIONS=sslmode=verify-full,sslrootcert=/certs/ca.pem`; v3 removed the former DB SSL variables. Stage the approved server CA PEM as `postgres-ca.pem` so the generated `paperless-postgres-ca` Secret mounts it read-only at `/certs/ca.pem`. The database certificate must match `PAPERLESS_DBHOST`. The tagged [Paperless configuration](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docs/configuration.md) documents this comma-separated option format. Its illustrative `sslmode=require` verifies encryption but does not verify the server hostname; [PostgreSQL recommends `verify-full`](https://www.postgresql.org/docs/current/libpq-ssl.html) for that assurance. Do not weaken this setting when selecting the endpoint.
- Replace `PAPERLESS_URL` with the external `https://` origin, without a trailing slash. It feeds host, CORS, and CSRF settings. Verify any forwarded-protocol setting against the actual ingress controller and prevent direct untrusted access to the Paperless Service.
- Select a CSI StorageClass and capacities for all four claims. Mounts match upstream at `/usr/src/paperless/data`, `/media`, `/consume`, and `/export`. `data` includes search indexes and classification state; `media` contains documents and thumbnails. The StorageClass must support cross-node detach/attach and UID/GID 1000 write access for the one active pod. The example uses `ReadWriteOnce`; change the consume claim only if a tested scanner intake design needs shared access. Polling is set to 30 seconds, which supports filesystems without inotify; tune this against intake latency and storage behavior. [Tagged setup](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docs/setup.md)
- Replace each NetworkPolicy CIDR with the observed and approved ingress-controller source, PostgreSQL endpoint, and broker endpoint CIDRs. Confirm the DNS pod labels, CNI enforcement, and actual packet source/destination addresses on RKE2. The policy denies all other namespace ingress and egress. Add narrowly scoped rules for mail, webhooks, Tika/Gotenberg, or remote OCR only if those features are enabled and tested.
- The optional [Tika/Gotenberg example](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docker/compose/docker-compose.postgres-tika.yml) adds both services for Office documents and `.eml`. This reference excludes them; enable both, pin their images, and add egress rules only when the approved intake formats require them.

## Secret and release boundary

Commit only `paperless.env.example` and `postgres-ca.pem.example`. Create the real `paperless.env` and `postgres-ca.pem` **only in the protected staged Kustomize tree** from approved sources, owned by root with mode `0600`; their directory and ancestors must also meet the Ansible protected-path checks. The CA PEM must contain the real issuing root certificate or approved chain for the selected PostgreSQL endpoint. Never add either staged input to the source repository, public provider bundle artifact, CI artifact, issue, or logs. The local `.gitignore` excludes them from normal Git adds, but Git ignore rules are not a secret-storage control. The staged tree digest, including both files' bytes, must be approved in the protected release manifest. Rotating either input changes its generated Secret name. The live-resource inventory rejects old Secrets left by `kubectl apply`. A rotation therefore needs a separately reviewed cleanup step after the new Pod is ready and no Pod uses the old Secret, but before final inventory verification. Delete only the exact prior Secret UIDs from a protected previous release record, with Kubernetes API deletion preconditions; retain the protected prior bundle for rollback. The current automation has no such cleanup step and deliberately fails closed on rotation.

The secret file supplies `PAPERLESS_SECRET_KEY`, `PAPERLESS_DBPASS`, `PAPERLESS_REDIS`, and initial administrator credentials. The secret key must remain stable across restarts; v3 refuses to start without it. The upstream [configuration](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docs/configuration.md) documents automatic administrator creation for Kubernetes when `PAPERLESS_ADMIN_USER` and `PAPERLESS_ADMIN_PASSWORD` are set. It does **not** rotate an existing user's password; rotate or remove initial credentials through a reviewed procedure after bootstrap. Do not use the example values in any environment.

Before authorizing production traffic, complete and review `ingress.yaml.example`, rename it to `ingress.yaml`, include it in the **staged** `kustomization.yaml`, and confirm the ingress class, `PAPERLESS_URL` host, TLS certificate source, HTTPS redirect behavior, and NetworkPolicy source CIDR. Stage it in the first-use bundle if certificate delivery is already verified. The example's ingress-nginx annotation is valid only for a selected ingress-nginx controller. An Ingress that references a missing TLS Secret or serves a default certificate does not pass TLS verification.

## Runtime and acceptance checks

The tagged image [supports rootless startup](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docs/setup.md) with UID/GID 1000 and no `USERMAP_UID` or `USERMAP_GID`. Additional `PAPERLESS_OCR_LANGUAGES` cannot be installed this way. Test the exact image digest with the selected CSI driver and pod security admission profile; this template does not assert that `readOnlyRootFilesystem` or dropping every capability has been validated. A cluster enforcing the [Restricted Pod Security Standard](https://kubernetes.io/docs/concepts/security/pod-security-standards/) will reject this template because the container does not yet declare `capabilities.drop: [ALL]`; add it only after testing the exact image and record admission evidence. Its `exec` probes follow the image's [localhost port-8000 healthcheck](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/Dockerfile). Tune startup, CPU, memory, and termination periods from a staging import and upgrade test. A web HTTP response does not prove scheduled tasks, OCR, database, broker, or storage integrity.

Keep one full Paperless replica with `Recreate`. The [upstream upgrade procedure](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docs/administration.md) requires quiescing consumption, taking a backup, stopping the old instance, and then starting the new image; startup applies database migrations. A three-node RKE2 cluster can reschedule this single pod but does not provide active-active Paperless availability. Verify backup and restore of PostgreSQL plus Paperless volumes. An upstream document export excludes API tokens and requires the same Paperless version for import. Existing v2 installations must reach v2.20.15 before a v3 upgrade. [v3 migration guide](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/v3.2.1/docs/migration-v3.md)

Use a protected control host to stage the reviewed files at `/etc/archiveweaver/paperless-ngx/kustomize`, inject the real secret there, and bind the complete tree digest to the release manifest before any Ansible apply. Render only to a protected sink for local checking; never print the rendered Secret or include it in diagnostics. Run the repository's signed-image, readiness, staging, failover, restore, and independent live-workload gates. This reference and static tests cannot establish a 100/100 production score without an actual pinned release, cluster, inventory, and evidence.
